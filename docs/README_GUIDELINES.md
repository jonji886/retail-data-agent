# README 编写规范

README 同时承担项目首页、解决方案简介和快速上手入口的职责。内容应服务于真实用户和第一次接触项目的开发者，不应编造效果或夸大能力。

## 内容优先级

建议按以下顺序组织：

```text
为什么需要 → 项目是什么 → 能解决什么 → 效果如何 → 如何使用 → 如何扩展
```

README 前部优先包含：

- 项目名称和一句话价值说明。
- 目标用户与适用场景。
- 输入、处理过程和输出示例。
- 可复现的效果指标或明确标注的待验证指标。
- 最小可运行命令。

先介绍业务价值，再介绍技术栈和目录结构。首次出现的专业术语应给出简短解释。

## 效果与证据

可以展示报告、问数结果、预警、归因、评测结果或界面截图。示例最好包含：

```text
用户输入 → 关键处理步骤 → 最终输出 → 来源、口径或评测证据
```

量化指标必须说明统计口径、数据来源、测试环境和运行命令。没有真实结果时，明确写出当前基线、预期目标和待验证指标，不使用“显著提升”等空泛表述。

## 架构与可视化

复杂的系统架构、数据流、Agent 工作流或模块关系优先使用 Mermaid、简洁表格或有信息价值的截图表达。

图示必须：

- 有标题和必要说明。
- 与当前实现一致。
- 在架构或流程变化后同步更新。

不要为了装饰添加无信息价值的图片。

## 快速开始

Quick Start 应让新人用最少步骤完成核心验证，至少说明：

- 环境要求。
- 安装与配置。
- 最小启动命令。
- 最小验证方式。
- 常见错误的排查入口。

不要把完整生产部署说明混入 Quick Start。

## 能力边界

明确说明：

- 适合的用户和业务场景。
- 当前支持的输入与输出。
- 数据、模型、性能和权限限制。
- 不适用的场景。
- AI 结果是否需要人工复核。

涉及高风险领域时，必须说明项目不替代专业判断，并写明当前用途和风险边界。

## 评测说明

AI 项目应尽量记录：

- 测试集来源和样本数量。
- 使用的模型或规则版本。
- 评测方法和运行命令。
- 准确率、成功率、引用正确率、延迟、Token 消耗或成本等适用指标。
- 已知 Badcase 和能力边界。

每个指标都应说明统计口径，避免只展示孤立数字。

## 更新检查

以下内容变化时检查 README：

- 核心功能、使用方式或配置。
- API、架构或数据流程。
- 效果指标、截图或示例。
- 能力边界和已知限制。

README 的详细结构可按项目规模调整，不要求机械包含 FAQ、Roadmap、License 等章节。

## 自检清单

- [ ] 新人能快速理解项目用途和目标用户。
- [ ] 前部有真实示例或可复现的最小体验。
- [ ] 关键指标有明确统计口径。
- [ ] 复杂流程有与实现一致的图示。
- [ ] Quick Start 可以直接执行。
- [ ] 已说明适用场景、限制和已知 Badcase。
- [ ] README 没有技术堆砌、虚构数据或夸大能力。
