# 经营决策视图设计说明

> 状态：第一版已实现，推荐追问按钮已支持点击自动执行；交互式下钻仍是后续增强。
>
> 目的：把 Agent 的可审计分析结果组织成公司老板和经营管理者可以快速判断、继续追问、采取行动的业务页面。当前 AI 分析助手已实现结论优先、KPI、贡献图表、核查建议和折叠技术依据。

## 1. 设计目标

老板打开页面后，应先得到三个答案：

1. 发生了什么：指标当前值、变化金额、变化比例和分析范围；
2. 为什么发生：哪些区域、门店、品类或渠道贡献了变化，以及证据是什么；
3. 接下来做什么：需要核查的经营线索、建议动作和可以继续追问的方向。

页面不应要求用户先理解 `Intent`、`Skill`、`Permission` 或 SQL 才能读懂结论。技术链路仍然保留，但默认收纳在“分析依据 / 执行详情 / 审计信息”中。

## 2. 推荐回答结构

### 2.1 结论区：结论先行

回答顶部固定展示：

| 信息 | 要求 |
| --- | --- |
| 分析范围 | 华东、华南、某门店等业务名称 |
| 分析期间 | 当前期间与对比期间，例如 2025-10 → 2025-11 |
| 核心指标 | 销售额、订单数、毛利额、客单价等 |
| 变化金额 | 使用货币格式，正负方向清晰 |
| 变化比例 | 同时展示绝对值和方向 |
| 数据状态 | 数据时间范围、更新时间或“固定种子演示数据”说明 |

结论应使用自然语言，而不是只显示结构化字段。例如：

> 华东区域 2025 年 11 月销售额为 ¥1,371,235，较 10 月下降 ¥475,460，降幅 25.75%。

### 2.2 贡献区：解释变化来自哪里

归因结果应拆成独立的表格或图表，不把多个门店和数字拼成一段长文本。推荐同时提供：

- 下降贡献 Top N 横向柱状图或瀑布图；
- 成员名称、当前值、对比值、变化额和下降贡献比例；
- 按门店 / 品类 / 城市 / 渠道切换的维度；
- 点击成员后继续追问或下钻。

“贡献率”必须标注为“数据变化贡献”，不能直接命名为“业务原因”。当前数据只能证明数值变化贡献，不能自动证明促销、库存、客流等业务因果。

### 2.3 判断区：区分事实、线索和因果

回答内容分为三层：

| 层级 | 表达方式 | 示例 |
| --- | --- | --- |
| 已验证事实 | 直接陈述，并可追溯到 SQL 和指标口径 | 上海旗舰店1店销售额下降 ¥130,920 |
| 待核查线索 | 使用“建议核查”“可能与……有关” | 建议核查该店订单数、客流和库存 |
| 已验证因果 | 只有存在外部业务证据时才允许使用 | 促销取消导致销售额下降 |

在没有客流、库存、促销或渠道数据时，系统不得把门店贡献直接解释成业务因果。

### 2.4 行动区：让结果可以继续使用

结论下方应提供 2～4 条与数据相关的核查建议，并支持一键生成后续问题，例如：

- “上海两家门店下降主要是订单数还是客单价导致的？”
- “华东下降最多的品类是什么？”
- “查看过去 6 个月华东区域销售趋势。”
- “比较华东与华南本月的销售变化。”

建议应来自可用数据和当前权限范围，不能凭空生成具体经营动作或承诺收益。

### 2.5 依据区：可审计但不打扰阅读

以下内容默认折叠，用户需要时展开：

- Query Plan 与意图；
- 权限判定与 Data Scope；
- Skill / Tool 调用链；
- 生成的只读 SQL；
- 指标口径、数据范围、Trace 和 Audit ID。

权限拒绝、安全拦截和分析失败仍应在页面上明确显示，不能被折叠后误认为成功。

## 3. 技术字段到业务表达的映射

| 当前字段或状态 | 面向业务用户的展示 |
| --- | --- |
| `store_name` | 门店 |
| `category_name` | 品类 |
| `attribution_analysis` | 销售变化归因 |
| `allow` | 已通过权限校验（默认不展示） |
| `passed` | 分析校验通过（默认不展示） |
| `Answer: generated` | 回答已生成（不作为业务结论） |
| `top_negative` | 主要下降贡献因素 |

技术字段可以在依据区保留原值，便于开发和审计，但不能成为老板主视图的主要标题。

## 4. 固定种子数据下的示例

问题：**为什么华东区域 11 月销售额下降了？**

推荐的业务呈现：

```text
结论
华东区域 2025 年 11 月销售额为 ¥1,371,235，较 10 月下降 ¥475,460，降幅 25.75%。

主要下降贡献
1. 上海旗舰店1店：下降 ¥130,920，贡献 27.54%
2. 上海标准店2店：下降 ¥120,485，贡献 25.34%
3. 杭州旗舰店3店：下降 ¥116,974，贡献 24.60%
4. 杭州标准店4店：下降 ¥107,081，贡献 22.52%

经营判断
华东 4 家门店共同造成下降，上海两家门店合计贡献约 52.88%。
上述是数据变化贡献，不等同于已验证的业务因果。

建议核查
- 上海两家门店的订单数、客流和客单价；
- 下降门店的重点品类、库存和促销变化；
- 是否存在渠道或数据采集异常。
```

示例数字来自当前固定种子演示数据；接入新数据源后，页面必须以实际查询结果、指标口径和数据时间范围为准。

## 5. 验收标准与当前状态

- [x] 老板无需阅读 Trace，即可在首屏理解范围、方向、金额和比例；
- [x] “为什么”问题返回可验证的贡献拆解，而不是只返回内部执行状态；
- [x] 贡献结果使用表格和横向柱状图呈现，避免长段落堆叠多个成员；
- [x] 技术字段默认折叠，异常、权限拒绝和错误状态明确可见；
- [x] 数字可以展开查看指标口径、SQL、Trace 和 Audit ID；
- [x] 回答明确区分已验证事实、待核查线索和业务因果；
- [x] 页面展示基于当前结果的后续追问入口；
- [x] 展示内容遵守当前用户的 RBAC 与 Data Scope，不因为可视化扩大数据权限；
- [ ] 点击贡献因素后自动下钻并执行后续问题；
- [x] 后续追问以可点击按钮直接回填并执行，并继承当前页面身份与 Data Scope。

## 6. 当前差距

当前 MVP 已实现第一版老板视角 AI 分析助手：业务结论、KPI 卡、主要下降贡献图表、贡献明细、核查建议和推荐追问；Intent、Skill、SQL、Trace 和指标口径默认收纳在分析依据中。贡献因素点击下钻和跨图表联动仍未实现；推荐追问已通过结构化 `recommended_questions` 和页面 Session 自动提交。后续改造应以本文档为产品验收基线，同时保持现有语义层、权限、只读 SQL 和审计边界不变。
